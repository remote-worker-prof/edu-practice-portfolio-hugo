# Откуда взялся синтаксис `agents-issue-workflow.cncf.yaml`

Этот документ объясняет происхождение синтаксиса файла `agents-issue-workflow.cncf.yaml` и теорию, на которой он основан.

## 1. Основа: CNCF Serverless Workflow

Файл `agents-issue-workflow.cncf.yaml` написан в стиле **CNCF Serverless Workflow** — это спецификация DSL (языка описания workflow), которая формализует структуру, состояния и переходы. Проект развивается в рамках CNCF как открытая и платформенно‑нейтральная спецификация.

В репозитории используется **спецификация версии 0.8**, что отражено в поле `specVersion: "0.8"`. Релиз v0.8 официально опубликован в истории спецификации.

## 2. Что такое “workflow definition” по спецификации

В спецификации v0.8 workflow‑определение описывается как YAML/JSON‑файл, содержащий набор обязательных и опциональных полей. Ключевые поля верхнего уровня включают:

- `id` / `key` — идентификатор,
- `name`, `description`, `version`,
- `specVersion` — версия спецификации,
- `start` — стартовое состояние,
- `states` — список состояний.

Это напрямую соответствует структуре нашего файла.

## 3. Состояния, переходы и завершение

В спецификации v0.8 основная логика workflow задаётся через **states**. Каждое состояние имеет тип, а переходы задаются явно:

- Для **Operation State** указываются `actions` и `transition` (или `end: true`).
- После выполнения actions происходит переход в следующее состояние.

В нашем файле используются именно **operation states**, потому что они напрямую описывают набор действий, которые выполняются последовательно.

## 4. Actions и FunctionRef

Внутри состояния типа Operation описывается массив `actions`. Каждое действие ссылается на функцию через `functionRef`.

- `Action Definition` допускает `functionRef` как ссылку на функцию.
- `FunctionRef` может быть строкой или объектом с `refName` и `arguments`.

Эта схема соответствует нашему файлу, где каждая action ссылается на функцию из блока `functions`.

## 5. `start` — откуда берётся точка входа

`start` в спецификации может быть строкой (имя стартового состояния) или объектом. В нашем файле используется строковый вариант — это самая простая форма задания точки входа.

## 6. Почему есть `functions` и `functionRef`

В v0.8 функции описываются отдельно как переиспользуемые блоки, а в состояниях они вызываются через ссылки. Это позволяет отделять **что делать** (state/action) от **как делать** (function definition).

## 7. Что в файле не является частью спецификации

В `agents-issue-workflow.cncf.yaml` есть поле `x-agent`. Поля с префиксом `x-` — это **локальные расширения**, которые не влияют на стандартную семантику спецификации и используются для внутренней логики инструмента.

## 8. Связь с нашим процессом

По сути, файл — это **машиночитаемая модель процесса**, где:

- `states` описывают шаги (createIssue → markInProgress → doWork → commit → close → sync),
- `functions` задают реальное выполнение (shell‑команды),
- `transition` определяет строгий порядок действий.

Такой подход полезен в агентной разработке, потому что порядок зафиксирован в DSL и легко проверяется.
